# Reflect — Priorities Review

**Read the dashboard (stated priorities) and the log (what actually got done), then: suggest
next steps, and discuss whether the priorities should change.** Ends in a conversation with the
owner ruling — never batch fixes. Boundary with [[lint]]: lint asks *is the repo well-formed*;
reflect asks *is the operational content still true and honestly prioritized*.

**Owner-triggered only.** Cadence: the monthly `Reflect` line in [[dashboard]] §Recurring suggests
it; the owner says go.

## Inputs (no script — evidence fits in context)

1. `dashboard.md` — the ranked priorities, and the dated lines that carry each one's next actions.
2. `log/log.md` entries **since the last `reflect` entry** (span into the `log-YYYY-qN.md`
   archives if needed; if reflect has never run, the owner names the window).

## The pass

1. **What got done.** Cluster the window's log entries by domain/priority — the picture of
   where effort actually went.
2. **Next steps.** For each dashboard priority, given what's now done: what's the highest-
   leverage next action? Confirm, sharpen, or replace the dated lines that carry it.
3. **Priority discussion.** Where stated order and demonstrated effort diverge, ask *which is
   wrong — the order or the effort?* Dashboard lines already past their date with no log
   movement get the same question: still real, or re-date / delete? Recommend a re-ranking if
   the evidence supports one; the owner rules.

While reading, flag (don't fix) facts whose `(verified:)` date looks old for their kind — program
rules, score cutoffs, processing times.

**The log is a proxy, not a record.** It captures what touched the *repo*; real effort (mock
exams, work conversations, networking) can leave no entries. A silent domain has two readings —
nothing happened, or the notes are behind — and reflect asks which, rather than concluding
"no progress." One answer is a priority question, the other a capture gap to backfill.

## Output

A short agenda — **cap ~5 items**, each: *evidence → question → recommended next step*, the
owner rules. The agenda is ephemeral (lives in the conversation, not a note). **No edits during
the run**; accepted recommendations become ordinary Updates afterwards.

## Verdicts (what persists)

- Each verdict is filed **into the owning note** — dashboard reorder, next-action change,
  re-verification task — per the normal Update function.
- A consciously deferred item gets a later date on its dashboard line, naming what brings it
  back, so sessions and later reflects skip it until then.
- One `reflect` log entry records the verdicts (it also anchors the next run's window); roll the
  dashboard's `Reflect` line forward a month; then Close.
